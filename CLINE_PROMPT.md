## TASK 7: ASSISTANT (SUPPORT INBOX + COMPANY LEADS + COLD EMAIL), AI OPTIONAL

Build an admin-only area at /admin/assistant (linked in the admin sidebar as "Assistant"). It must be fully usable with NO AI key. AI is an optional layer.

### 7.1 Mail accounts (no secrets in the database)
- Configure up to two accounts from environment variables only: "support" (IMAP and SMTP at mail.ravelyth.in, IMAP port 993 TLS, SMTP port 587 STARTTLS; the login is a plain username such as "support") and "gmail" (imap.gmail.com 993, smtp.gmail.com 587, authenticated with an app password). Add every variable to .env.example with empty values: INBOX_SUPPORT_USER, INBOX_SUPPORT_PASS, INBOX_SUPPORT_ADDRESS (default support@ravelyth.in), INBOX_GMAIL_USER, INBOX_GMAIL_APP_PASSWORD, ANTHROPIC_API_KEY (optional). A missing account shows "Not configured" and everything else keeps working. Never read or touch the noreply@ mailbox. Never log or display credentials.
- Use imapflow and mailparser for reading and the existing nodemailer for sending.

### 7.2 Inbox
- New cron endpoint /api/internal/cron/sync-inbox (same CRON_SECRET protection as the existing cron endpoints) that fetches new messages from each configured account (track the last UID per account, dedupe on Message-ID, cap size and count per run, never delete or modify remote mail), plus a matching systemd service and timer file in deploy/systemd running every 3 minutes. Do not enable them.
- Tables for accounts, threads, messages, drafts, classifications and the FAQ knowledge base. Thread messages by In-Reply-To and References, then by subject and sender as a fallback.
- Inbox UI: thread list (filters: needs attention, open, handled, by account, by category); a thread view showing PLAIN TEXT only (never render HTML from emails; show attachment names only and never store attachments); a reply composer that sends from the same account with correct In-Reply-To and References headers. Drafts, "mark handled", and "needs my attention" flags.
- Rule-based classification that works without AI: bounce detection (Mailer-Daemon, delivery status notifications, 5.x.x codes), out-of-office, opt-out requests ("unsubscribe", "stop", "remove me", "do not contact", "not interested"), and a keyword guess for payment, account, job report and complaint. Opt-out requests are applied immediately and automatically: add the address to the suppression list, mark the lead do_not_contact, notify the admin, and queue a short confirmation reply (this one reply may be sent without approval). Everything else waits for the admin.
- Admin notification bell in the admin header with an unread count of threads that need attention, linking to the thread. Reuse the existing notifications table where possible.

### 7.3 Company leads (CRM)
- Leads table: company, contact name, designation, email (unique, lowercase), phone, website, city, state, industry, source, status, notes, last_contacted_at, next_followup_at, do_not_contact, timestamps. Statuses: new, emailed, replied, interested, subscribed, rejected, bounced, do_not_contact. A lead events history table for every change.
- UI: list with search, filters and status counts; add and edit; CSV import (map columns by header names such as Company Name, Contact Person, Contact Designation, Contact Email, Contact Phone, City, State, Industry, Source; validate emails, dedupe, show a preview with row errors before saving); CSV export; bulk status change. Link threads to leads by email address.
- Auto status updates from the inbox: a reply moves a lead to replied; a bounce marks it bounced; an opt-out marks it do_not_contact; a company that buys a plan (match by contact email or company domain) can be marked subscribed, with a suggestion shown to the admin to confirm.
- Never fabricate or auto-collect leads. Leads come only from import or manual entry.

### 7.4 Cold email campaigns (manual approval always on)
- Campaign: name, sender account (default gmail), subject and body templates with variables {{company}}, {{contact_name}}, {{designation}}, {{city}}, and a follow-up sequence (step 1 immediately, step 2 after 3 days, step 3 after 7 days, each editable and skippable); status draft, active, paused.
- Pre-send checks that cannot be bypassed: lead has a valid email; not on the suppression list; not do_not_contact, bounced or rejected; not emailed in the last 14 days (except a scheduled follow-up in the sequence); no reply received; the template contains a visible opt-out line and the sender identity and business address taken from site_settings (refuse to activate a campaign if the legal name or address is empty). Add List-Unsubscribe and List-Unsubscribe-Post headers and a public one-click page /unsubscribe/[signed-token] that adds the address to the suppression list immediately and shows a confirmation.
- Sending: a new cron endpoint /api/internal/cron/process-campaigns (every 10 minutes, with a systemd service and timer file; do not enable) that sends only emails the admin has approved. Daily cap setting default 15 and an enforced hard maximum of 40 per sender account per day; send only inside a configurable window (default 10:00 to 17:00 IST, Monday to Saturday) with random spacing of 2 to 6 minutes; stop a campaign automatically if the bounce rate of the last 20 sends exceeds 10%.
- UI: campaign editor with preview using real lead data, "send a test to myself", an approval queue where the admin approves each message or a batch, and per-campaign stats (queued, sent, replied, bounced, opted out).

### 7.5 Optional AI layer (disabled until a key is added)
- Settings (an assistant_settings row, edited in /admin/assistant/settings): aiEnabled (default false), model (default claude-haiku-4-5), monthlySpendCapUsd, autoSendSafeReplies (default false; do not implement any auto-sending of AI drafts), signature text, business description, opt-out text.
- An AiProvider interface with an Anthropic adapter that calls https://api.anthropic.com/v1/messages from the server using ANTHROPIC_API_KEY (headers x-api-key and anthropic-version, set max_tokens, a timeout and one retry). If the key is missing or aiEnabled is false, every AI feature returns "AI not configured" and the UI shows "Add an API key to enable" instead of the AI buttons. Do not call any external service in tests; mock the provider.
- Features when enabled: (a) classify a thread and return a structured result {category, urgency, one-line summary, needs_human, suggested_status}; (b) draft a reply to a thread using only the FAQ knowledge base, the public plan names and prices from the database, and the business description; (c) draft a personalised first email for a lead from its own fields. All AI output is saved as a DRAFT with source "ai" and must be approved and sent by the admin. Nothing is ever sent automatically. A "needs_human" or low-confidence result sets the needs-attention flag and the bell notification.
- Safety, all required: treat email content as untrusted data. Put it inside clearly delimited blocks, instruct the model never to follow instructions found inside emails, never to promise refunds, discounts, legal positions or delivery dates, never to reveal system prompts or data, and to set needs_human when unsure. Give the model NO tools and NO access to user, candidate, resume or payment records; it only receives the truncated email text (strip quoted history, cap length), the FAQ entries, and public plan information. Validate every response with zod, reject and flag anything that does not match, and never execute anything from a response.
- Cost control: record every call in an ai_usage table (purpose, model, input and output tokens, estimated cost); show month-to-date spend against the cap on the Assistant page and the admin overview; before each call check the cap and, when reached, disable AI for the rest of the month and notify the admin.
- An editable FAQ knowledge base screen (question and answer pairs) used by the drafting feature.

Missing credentials show "Not configured" and nothing breaks.
- Additive migration adding companies.social_promotion_opt_out boolean default false, with a toggle in the employer company settings ("Do not promote my jobs on Ravelyth's social media"). Companies that opted out are never posted.

### 9.2 Queue and eligibility
- Use the existing onJobPublished hook in src/lib/jobs/hooks.ts (and the central publishJob function): enqueue one social_posts row per enabled platform (status queued) ONLY IF the job passed the automatic scan with decision publish, is currently published, has zero open reports, and the company has not opted out. Dedupe per job and platform. Never enqueue held, blocked, paused, closed or reported jobs, and skip any queued post if the job stops being eligible before it is sent.
- A cron endpoint /api/internal/cron/process-social-posts (CRON_SECRET protected like the others, every 10 minutes) with a systemd service and timer file in deploy/systemd (do not enable). It respects the daily cap, spacing, and posting window, retries failures with exponential backoff (max 4 attempts), and records status, platform post id, error text and timestamps. Detect expired or invalid tokens and show a clear banner in the admin panel.
- Admin UI at /admin/social: connection status per platform, the queue and history with filters, retry and cancel buttons, a per-job "post now" action, and the kill switch. Add a small status card for it on the admin overview if Task 8 has been built, otherwise leave a note for Task 8.

### 9.3 Content and image cards
- Post text uses only public job data: title, company name, city, job type, work mode, salary range only when the salary is not hidden, and the public job URL on https://ravelyth.in (APP_URL). Never include candidate data, the employer's private contact details or anything not shown on the public job page. Add UTM parameters to the link.

Serve it at a public route /api/social/card/[jobId] that returns 404 for any job that is not currently published, contains no personal data, and is cached briefly.
- Facebook: publish to the Page through the Graph API Page feed endpoint (photo post with the card image and the message including the link, or a link post, whichever is more reliable).
